## 1. 项目目标与当前主线

本项目研究具身智能 AI 相关软件基础设施的漏洞，重点是：

1. 通过源码审计、模糊测试和最小 PoC 发现模型解析、配置解析、消息处理等缺陷；
2. 在精确版本和 commit 上完成可复现证据；
3. 横向比较不同组件中的共同根因；
4. 与导师分享已经发现的漏洞，再共同判断是否值得开展“真正的攻击”验证；
5. 在案例足够可靠后形成综述或论文。

当前采用的研究顺序：

```text
漏洞发现/审计
  → 最小复现
  → 版本、修复状态、公开状态核验
  → 统一案例登记
  → 共通根因归纳
  → 与导师讨论攻击价值和授权边界
  → 经明确同意后才考虑 L3/L4 离线/仿真验证
  → 综述/论文案例章节
```

### 已明确的路线决策

- **放弃 ONNX/ONNX Runtime 后续路线**：不再继续 ORT fuzz campaign，不再把 ONNX/ORT 作为新目标；旧 ONNX 文档保留为历史记录，不能当作当前计划或已核验结论。
- **当前目标池**：NCNN、MindSpore、`agibot_x1_infer`，以及作为第四候选的 `genie_sim`。
- **研究组织方式**：采用“证据收敛优先 + 综述骨架同步维护”。建议约 70% 时间用于漏洞复核/新审计，约 30% 用于案例库和综述材料。
- **新增工具线（2026-08-22）**：cwe-repair 防御侧工具（DSH skill，v7）——导师建议"从防御者角度设计自动化检测和修复特定类型漏洞"；与漏洞案例线并行（工具反哺发现：MNN Interpreter 截断新漏洞）。
- **暂不做 L3/L4**：目前只整理漏洞本身的根因、复现、影响边界和修复状态；不主动收集“漏洞导致动作轨迹或真实攻击结果”的证据。
- **不保存用户学生身份到 memory**：用户已明确要求不保存这一背景。不得再次写入长期 memory。

## 4. 综述/论文写作方案

### 4.1 不立即写成结论的核心原则

综述当前不是把已有漏洞简单拼接，而是建立“证据库 → 分类法 → 可验证论点”。每个论点都要能回到：

- 精确版本/commit；
- 源码位置；
- 可复现输入和日志；
- 修复 diff 或公开公告；
- 明确的证据等级。

未经核验的论文、CVE、市场数字和攻击影响只能标记为“待核验”，不能当作事实。

### 4.2 建议论文/综述题目方向

暂定方向（不是最终题目）：

> 面向具身智能软件供应链的模型与控制栈输入验证漏洞研究

可能的英文工作线：

> Input-Validation Failures in Embodied-AI Software Supply Chains: A Case Study Across Inference Engines and Robot Software

不要在标题中提前声称 RCE、物理危害或系统性普遍结论。

### 4.3 建议章节结构

1. **引言**
   - 具身智能由模型、推理引擎、机器人软件栈和仿真平台组成；
   - 模型/配置/消息文件跨越多个信任边界；
   - 现有研究多讨论模型或控制攻击，较少统一比较底层软件输入验证缺陷；
   - 本文贡献限定为案例和方法，不夸大攻击等级。

2. **背景与系统边界**
   - 模型供应链、推理引擎、机器人控制软件、仿真平台；
   - 区分模型文件、配置文件、消息和场景资产；
   - 定义攻击者能力：恶意模型/畸形本地输入，不默认拥有网络或设备权限。

3. **研究方法**
   - 入口地图；
   - 历史修复 diff；
   - 结构化 fuzz/最小 PoC；
   - ASan/UBSan/正常构建 A/B；
   - 版本和公开状态核验；
   - 负面结果与重复漏洞排除。

4. **统一分类框架**
   - 计数/长度/维度未校验；
   - 索引/范围未校验；
   - 二进制与文本或不同入口修复不对称；
   - 整数溢出与资源放大；
   - 异常/清理路径错误；
   - 模块接口数组/状态假设不一致。

5. **案例分析**
   - NCNN 参数解析家族；
   - MindSpore checkpoint 加载家族；
   - AGIBOT 控制/仿真消息与配置候选；
   - GenieSim（只有完成静态或运行证据后才加入）。

6. **跨案例比较**
   - 输入类型、信任边界、根因、影响、默认可达性、修复对称性；
   - 区分真实测量和源码推断；
   - 不把“模型可投递”自动等同于远程攻击。

7. **防御建议**
   - 统一长度/范围/维度校验；
   - 跨格式入口一致性检查；
   - 资源预算和拒绝策略；
   - 消息 schema 与数组长度契约；
   - 仿真和真实部署配置隔离；
   - 修复后回归样本和版本发布流程。

8. **局限性与后续工作**
   - 未连接真实执行器；
   - 未开展 L3/L4；
   - 未研究 RCE；
   - 许多案例依赖本地输入或特定配置；
   - 后续是否进行更高影响验证须经导师和明确授权共同决定。

### 4.4 统一案例表字段

每个案例至少记录：

| 字段 | 说明 |
|---|---|
| 组件/版本 | tag、commit、构建选项 |
| 外部输入 | 模型、配置、消息、场景/资产 |
| 信任边界 | 输入来源与权限 |
| 入口 | 函数、文件、行号 |
| 根因 | 具体校验或状态缺陷 |
| 最小触发条件 | 输入大小、格式、配置 |
| 影响 | 资源耗尽、崩溃、越界读写、异常接受等 |
| 证据等级 | 实测/源码/公开资料/待验证 |
| 修复状态 | 未修、fork 修复、上游合入、发布版本 |
| 公开状态 | 私密、公开、重复、待核验 |
| 具身关联 | 感知/规划/控制/仿真/供应链 |
| 是否适合后续攻击验证 | 仅记录待导师讨论，不自行推进 |

### 4.5 综述写作节奏

- **阶段 1：材料清洗**：统一事实、版本、证据等级和公开状态；
- **阶段 2：分类草稿**：只用已证实案例提出分类，不扩张结论；
- **阶段 3：案例章节**：每个案例按同一模板写，保留负面结果；
- **阶段 4：比较与防御**：从案例中归纳共通点，并标注哪些仍是研究假设；
- **阶段 5：导师审阅**：分享不含未公开触发器的版本，讨论是否增加真实攻击/仿真验证章节；
- **阶段 6：定稿**：逐条核验引用、版本和公开状态后再形成对外稿件。

## 5.5 cwe-repair 防御侧工具线（2026-08-22 新增，完整历程）

> 定位：导师建议"从防御者角度设计自动化检测和修复特定类型漏洞"→ 开发 DSH skill
> 「cwe-repair」——针对 C/C++/Python 特定 CWE 类型的「检测→修复→正确性验证」闭环。
> 详细逐轮日志（含全部踩坑）：`研究文档/cwe-repair开发日志-2026-08-22.md`；
> 本节为交接用完整历程浓缩。

### 5.5.0 起点与动因（2026-08-20）

- **导师建议**（原话要点）："找能升级到任意代码执行级别的漏洞本身就很难，做漏洞利用问 AI 还会被安全护栏限制。能不能从防御者角度设计自动化检测和修复某一种特定类型（内存越界、整数溢出、逻辑错误）的 bug？"
- **前期诚实评估**：检测/修复/验证单拎出来都是成熟红海（Coverity 2002、APR 2009、LLM 修复 2025 已产品化）；真正缺口是**组合 + 垂直场景**——「提交前最后把关 + 修复有效性证明」。
- **定位**：不是更强的扫描器，而是 **「修复正确性双向验证」+「成对入口对称性检查」**——后者经调研确认无同类工具。

### 5.5.1 开发时间线（v1 → v7，2026-08-20 至 08-22）

| 版本 | 日期 | 核心工作 | 关键结果 |
|---|---|---|---|
| v1 | 08-20 | 三脚本初建（detect/repair/verify），模式来自 28+ 实证漏洞 | AR-1 L170 命中、补丁生成、模拟 verify 闭环 |

### 5.5.5 新漏洞发现（工具驱动）

- **MNN issue #3595**（FileLoader::read size 无校验）：工具命中 ground-truth，**最新 master 仍未修复**；
- **MNN Interpreter::createFromBuffer 截断**（新，未公开）：`(int)size` 截断 + 按原 size memcpy → 越界写（公开 API 入口），详见 `TOOLTEST_MNN/MNN-Interpreter截断漏洞-2026-08-22.md`；
- **MNN FileLoader::merge 截断候选**（`(int)mTotalSize`，>2GB 越界写，待大文件验证）；
- **可 PR 补丁 ×2**：`AGIBOT/上报材料/fix-x1_infer-jointcmd-parallel-array.patch`（X1-4）、`fix-x1_infer-writemotorcmd-oob.patch`（X1-5）——git apply 验证可应用。

### 5.5.6 负面结果（论文价值）

onnxruntime v1.28.0 / Paddle-Lite 核心解析器**已加固**（维度/溢出/CHECK 断言）→ 无新漏洞；
结论：工具在"未加固中小组件"高产出（agibot 14 缺陷、XR 6 漏洞、MNN 2 截断）——
**扫描优先级 = 低维护/无安全流程组件**。

### 5.5.7 方法论沉淀（跨迭代）

1. **漏洞驱动的工具迭代**：真实扫描发现的漏洞形态 → 扩展模式库 → 生成对应修复模板 → 回归验证（v6 截断、v7 跨行均由扫描驱动）；
2. **基准量化驱动改进**：leaderboard 暴露的检出缺口 → 针对性迭代（跨行/CWE 同族）→ 32%→48%；
3. **真实环境验证不可替代**：exit code vs ret 输出 vs 信号码的语义差异，模拟测试永远发现不了（v5）；
4. **负面结果有价值**：ORT/Paddle-Lite 无新漏洞 = "目标已加固"的实证，指引扫描优先级；
5. **诚实边界**：detect 是"初筛器"非"精确扫描器"（48% 检出 = 需 agent/人工核验）；逻辑类（CWE-306/502/78）需不同模板。

### 5.5.8 边界与纪律（沿用项目规则）

- 防御侧：不生成利用代码、不研究 RCE 利用链；
- 修复必须验证（未跑 verify 视为未完成）；生成补丁须人工审阅；
- 工具内发现的新漏洞（MNN Interpreter 截断）**未上报**，PoC 保持私密，待与导师确认披露策略。
