2. Problem Description
----------------------
MindSpore load_checkpoint() has a heap buffer overflow (CWE-787) when parsing a malicious .ckpt model file, leading to memory corruption.

The .ckpt file is protobuf-based. The TensorProto contains two attacker-controlled fields: dims (declared tensor shape) and tensor_content (actual data bytes). The Python side serialization.py does NO length validation; it passes both directly into C++ Tensor_.convert_bytes_to_tensor() -> ConvertBytesToTensor (ccsrc/pybind_api/ir/tensor_py.cc:538-548) -> CopyFromBuffer (tensor_py.cc:504-537).

Root cause: in CopyFromBuffer:

    size_t remain_size = src_size;                            // copy length = attacker-controlled content length
    auto ret = memcpy_s(dst_ptr, remain_size, src_ptr, remain_size);  // src length used as dest buffer size

The second argument of memcpy_s should be the remaining size of the DEST buffer (for safety checking), but the code passes remain_size (= src remaining length). The dst_size parameter is never read in the non-bf16 branch -- the safe function is bypassed. When tensor_content length > expected size derived from dims (tensor->Size()), data is written past the too-small buffer -> heap overflow.

3. Occurrence Scenario
----------------------
- OS: Ubuntu 22.04 x86_64 (WSL2 also verified)
- Attack scenario: poisoned model weights on HuggingFace / ModelScope -> user calls load_checkpoint -> triggered
- No privileges required; user must actively load the file (same scenario as official CVE-2026-24747 PyTorch)

4. Impact
---------
- Direct: glibc heap metadata corruption -> process exit with "free(): invalid next size (fast)" -> SIGABRT deterministic crash
- Potential: heap out-of-bounds write (>=32B reliably corrupts chunk header) has memory-corruption primitive potential; in principle upgradable to arbitrary code execution (requires heap grooming under modern glibc, medium-high difficulty)
- Relationship to the public DoS: same root (unvalidated tensor_content length), two manifestations -- large dims -> CWE-789 memory amplification (40GB from 32B file); small dims + large content -> CWE-787 heap overflow (this report)

5. Reproduction (manually verified, 2026-08-07, MindSpore 2.8.0)
-----------------------------------------------------------------
    python craft_poc.py float32     # generate poc_heapoverflow.ckpt (279B): dims=[2] expects 8B + 256B content (32x)
    python trigger.py poc_heapoverflow.ckpt

Actual output:
    RETURN-NORMALLY                          # load_checkpoint returns without error (overflow already written)
    free(): invalid next size (fast)         # glibc detects heap corruption
    Aborted (core dumped)                    # SIGABRT (rc=134)

Key: the crash occurs at interpreter shutdown, when the tensor is destructed -- the caller cannot catch or defend against it.

Cross-type evidence (Int4):
    python craft_poc.py int4       # int4_d2_c64.ckpt (81B): dims=[2] qint4x2 expects 1B + 64B content
    # -> same free(): invalid next size

Affected code locations (master):
- mindspore/ccsrc/pybind_api/ir/tensor_py.cc:504-537  CopyFromBuffer (dst_size never read)
- mindspore/ccsrc/pybind_api/ir/tensor_py.cc:538-548  ConvertBytesToTensor
- mindspore/train/serialization.py:~1268-1279        (no validation on Python side)

6. Suggested Fix
----------------
1. Entry validation (Python side): before load_checkpoint, check len(tensor_content) == prod(dims) * itemsize; reject on mismatch
2. C++ side (fundamental fix): in CopyFromBuffer, pass the real remaining dest size to memcpy_s, and validate PYBIND11_BYTES_SIZE == tensor->Size():

    if (PYBIND11_BYTES_SIZE(bytes_obj.ptr()) != tensor->Size()) {
        MS_LOG(EXCEPTION) << "tensor content size mismatch";
    }
