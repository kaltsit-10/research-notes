## 三、核心认知：ORT 本体 ≠ 库层（为什么停掉抽奖）

### 我们之前 fuzz 的是什么

```
恶意 .onnx 模型文件
    ↓
[库层] onnx.proto 生成代码 + libprotobuf 3.12.4   ← 之前 fuzz 的就是这层
    ↓
[ORT 本体] onnxruntime/core/ 的 C++ 代码
    ├── graph.cc / model.cc     模型加载、图构建
    ├── graph_viewer.cc         图优化
    ├── shape 推断              张量尺寸计算
    ├── session/                会话管理
    ├── allocator/              内存分配
    └── kernels/                算子执行
    ↓
硬件
```

### 停掉"抽奖"的三个理由（诚实评估）

1. **protobuf 是 Google 天天 fuzz 的库**（OSS-Fuzz）。一台 CPU 跑 8 亿次，想发现 Google 全球算力没发现的 bug，概率极低。3.12.4 还是老版本，bug 大多已知/已修。
2. **cov 已饱和**（2573→2588 放缓）：简单路径探索完了，深层代码朴素 fuzz 够不到。
3. **第一个 crash 恰好在库层**：证明就算再找到几个，大概率还是 protobuf 的 bug，不是 ONNX Runtime 的 CVE。

> **一句话**：一直跑当前这个自动化 fuzz 是"低概率碰运气"。fuzz 本身没错，是**目标选错了**。

## 四、转向决策：fuzz ORT 本体

### 为什么转（期望值对比）

> ⚠️ **2026-08-04 重大修正**：ONNX Runtime **不发表 CVE**（走 MSRC VULN-#### 私密追踪，证据：issue #23258 → VULN-143188，无 CVE）。"fuzz ORT → 拿 CVE"的旧假设不成立。

| 目标 | 出 CVE 吗 | 出什么成果 | 说明 |
|------|----------|-----------|------|
| 库层（protobuf）— 已停 | ❌ | 低 | Google 已 fuzz 烂 |
| **onnx 包自己代码**（version_converter/checker/external_data） | ✅ **有 CVE** | CVE 编号 | 2026 年刚出 Gemm/Upsample 堆 bug，CVE 流程健全 |
| **ORT 引擎** | ❌ 只有 VULN-#### | 论文+披露致谢 | 真实高危 bug，报 MSRC，无 CVE |
| CVE 系统性分析（综述） | — | 保证出 | 第一个确定能拿到的成果 |

### 现成的官方 harness（已确认存在，未构建）

```
~/fuzz-lab/onnxruntime/                ← onnxruntime 1.29.0 已克隆
    ├── fuzz/fuzz_onnx_model.cc        ← 官方 libfuzzer 目标（调 Model::Load）
    └── onnxruntime/test/fuzzing/      ← 官方 fuzz 基础设施
```

构建它（cmake + clang + ASAN，约 0.5-1 小时）就能 fuzz **真实的 ORT 本体代码**——
那里才是历史 CVE 的所在地。
