## 三、复现 2：NCNN 两个漏洞（核心成果）

### 2.1 CVE-2026-50144：负 ID 堆越界写（已修复）

**根因**：`id` 为负（如 -5）时，`id >= NCNN_MAX_PARAM_COUNT` 恒 false → 负索引 `params[-5]` → 越界写

**修复 diff（commit 5a0288f2，text 与 bin 两处）**：
```diff
-        if (id >= NCNN_MAX_PARAM_COUNT)
+        if (id < 0 || id >= NCNN_MAX_PARAM_COUNT)
```

**复现对比**：
| 构建 | 结果 |
|------|------|
| 漏洞版 20260526 + ASAN | SEGV on WRITE @ paramdict.cpp:612 |
| master（已修） | `id < NCNN_MAX_PARAM_COUNT failed (id=-5)` → 拒绝 |

### 2.1.5 ⭐ 修复状态确认：DoS 在最新版仍未修

装了 MindSpore **2.10.0（最新）** 同样复现：`Try to alloca a large memory, size is:40000000000`
→ **2.8.0 + 2.10.0 均受影响** → 可上报华为/CNVD（已知但无 CVE，官方未处理）

### 2.2 ⭐ 96B NULL 解引用（**未修复**，潜在新 CVE）

**根因**：数组分支 `len` 完全未校验
```cpp
d->params[id].v.create(len);         // len=INT32_MIN → 符号扩展 exabyte 级分配 → 失败返回 NULL
float* ptr = d->params[id].v;        // ptr=NULL
nread = dr.read(ptr, sizeof(float) * len);  // fread 写 NULL → SIGSEGV
```

**关键证据**：在 **master（已修 CVE-2026-50144 的最新代码）** 上 96 字节 PoC 仍崩溃：
- 普通版：Segmentation fault（exit 139）
- ASAN：`allocation-size-too-big 0xfffffffe00000044` @ paramdict.cpp:591

**为什么 CVE 补丁没修它**：CVE-2026-50144 是 `id<0` 检查（防负索引）；96B 是 `len` 未校验（id 合法，是分配大小问题）——**两个不同分支、不同根因，同文件**。只修了前者。

**不对称证据**：`modelbin.cpp` 有 5 处 `Mat::empty()` 防护；`paramdict.cpp` 数组分支 0 处。

### 2.3 变体扩展：text 格式也有同款 bug（系统性审计）

审计 text 版数组分支发现同类问题：
- **bin 版**：`len=INT32_MIN` → Mat::create 失败返回 NULL → `dr.read(NULL)` → **SIGSEGV（干净，必现）**
- **text 版**：`len=INT32_MAX`（数组标记 `-23300=2147483647,1.0`）→ create 失败 → 未捕获异常 → **abort（exit 134）**
- 注意：text 版负 len 不崩（`j<len` 循环不执行）；字符串分支有 `len>255` 检查相对安全

→ 同一家族（len 未校验）在两种格式都有，bin 版是最干净的触发。

## 七.6、⭐ 变体审计重大发现：MindSpore CWE-787 堆溢出（DoS 升级为内存破坏）

**用户要求审计"dims 变体（负数/溢出→越界？）"，结果远超预期：从 DoS 挖出一个全新堆溢出漏洞。**

### 触发
- `dims=[2]`（Float32，期望 8B）+ `tensor_content=256B` → **8B 缓冲写 256B → 堆破坏**
- 279 字节 .ckpt，`poc_heapoverflow.ckpt`

### 决定性证据
```
load_checkpoint 返回成功（RETURN-NORMALLY）→ 析构时 glibc 检测到堆破坏：
  free(): invalid next size (fast) → Aborted (core dumped)
2.8.0 + 2.10.0（最新）均触发；MALLOC_CHECK_=3 确认
```

### 根因（源码铁证，master tensor_py.cc）
```
ConvertBytesToTensor (538-548):
  tensor = make_shared<Tensor>(type, shape)    // 按 dims 分配
  CopyFromBuffer(dst, tensor->Size(), src, PYBIND11_BYTES_SIZE(bytes), type)

CopyFromBuffer (504-537):  ← 漏洞本体
  size_t remain_size = src_size;               // 拷贝长度 = 内容长度（攻击者控制）
  memcpy_s(dst_ptr, remain_size, src_ptr, remain_size)
  // ★★★ dst_size 参数在非 bf16 分支完全没被读取！
  // ★★★ memcpy_s 第二个参数（本应是 dest 缓冲大小）传的是 src 剩余大小
  // → 安全函数被绕过：src_size > dst_size 时堆溢出
```

### 边界测试
| 内容长度 (dims=[2] 期望8B) | 越界 | 结果 |
|---|---|---|
| 8B | 0 | 正常 |
| 12-24B | 4-16B | 静默（写进 heap 空隙） |
| **≥32B** | **≥24B** | **稳定崩溃** |

### 方法论收获
1. **审计"已知漏洞的兄弟方向"比从零挖快**：已知 DoS = "dims 大内容小"，反方向"dims 小内容大"就是堆溢出——同一个校验缺失的两个侧面
2. **`memcpy_s` 不等于安全**：`memcpy_s(dst, size, src, n)` 的 size 传错照样溢出；检查安全函数的参数来源是否可信
3. **崩溃点 ≠ 漏洞点**：gdb 栈显示崩溃在 `Py_FinalizeEx → ClearAttrAndMethodMap → _int_malloc`（heap 元数据破坏的下游），真正的写点在更早的 CopyFromBuffer —— 需要行为分析（边界阈值）+ 源码定位才能找到

### 与 DoS 对比（同一根因两种表现）
| | DoS (CWE-789) | 本发现 (CWE-787) |
|---|---|---|
| dims/content | 大 dims + 小 content | 小 dims + 大 content |
| 现象 | 40GB 分配 OOM | 8B 缓冲写 256B |
| 影响 | DoS | **内存破坏（潜在 RCE）** |
| 修复 | 2.8.0+2.10.0 未修 | **2.8.0+2.10.0+master 均未修** |

### bf16 特判分支验证（后续）
- 假设"dst 每步2B src 每步4B 会越界" → **错误，被实证推翻**
- 数学：触发条件 `dst_size*2==src_size`，写入总量 = elem_num*2 = (src_size/4)*2 = src_size/2 = **dst_size** → 正好写完，有界安全
- 实测 6 个 case 确认：exact-2x 全 clean；bf16 溢出仍只在 else 分支（content>dst），同阈值 ≥24B 越界
- **教训**：看到"循环里指针步长不一致"先算总量再下结论，别凭直觉假设越界

## 七.8、CopyFromBuffer 家族审计：单点入口，无第二漏洞（08-07 晚）

**用户要求深挖"是否有同样或差不多的漏洞"，结论：CopyFromBuffer 是单点，无同款第二入口。**

| 检查项 | 结果 |
|------|------|
| `CopyFromBuffer` 调用者 | **只有 1 个**：`ConvertBytesToTensor`(547行) |
| Python 侧 `convert_bytes_to_tensor` 调用 | **只有 1 处**：serialization.py:1279 |
| `load_checkpoint` / `load_checkpoint_async` | 全部收敛到 1279 → 同一漏洞点 |
| safetensors 格式 | 走 `_fast_safe_open`（safetensors 库），**不经 CopyFromBuffer** |
| `load()` MindIR | 走 `load_mindir` C++ 独立解析链 → **独立家族，待审** |
| `_parse_ckpt_proto` | 只 `ParseFromString`，**零 content/dims 关联校验** |

**Python 侧零校验**（serialization.py:1268-1279）：
```python
data = element.tensor.tensor_content   # 攻击者控制
dims = element.tensor.dims             # 攻击者控制
...
param_data = Tensor_.convert_bytes_to_tensor(new_data, tuple(dims), ms_type)
```
**没有任何 `len(content) == prod(dims)*itemsize` 校验**。整个加载链唯一防线就是 C++ `CopyFromBuffer`，而它 `dst_size` 被忽略——漏洞必然存在的原因。

**排除的疑点**（避免误报浪费）：
- `MemCopyFromCacheToHost`(450行) host_offset 越界 → `LongToSize` 对负值有保护 + 需 cache-enabled tensor（非文件解析入口）→ 攻击面窄
- `MakeTensorOfNumpy`/`SyncAsNumpy` → numpy buffer 自洽，安全
- `AsNumpyOfSlice` → 需 persistent tensor（非文件入口）
- `_load_map_parameter`/`str` 分支 → numpy reshape 校验一致性，异常非内存破坏

**证明堆溢出不是 Float32 特例，所有类型（含 2 元素打包 1 字节的 qint4x2）都受影响。**

## 七.12、Task 2：dims 截断/负值变体全矩阵审计（"测试2"，08-07 晚）

**cast<int> 截断假设被推翻**：int64→int32 超界（2147483648 等）→ 抛 RuntimeError，**无回绕**（早期"截断变体"假设错误，已修正）。但 **int32 范围内负 dims（-1/-5/-100/-2147483648）全部通过 cast** → 负值是真实攻击面。

**588 case 矩阵（2.8.0 实测：6 dtype × 14 dims × 7 content 长度）**——所有 dtype 除一处外完全一致：

| dims | 4 | 8 | 16 | 24 | 32 | 64 | 256 |
|---|---|---|---|---|---|---|---|
| (empty)/0/1/2/3 | O | O | O | O | **C** | C | C |
| 10 | O | O | O | O | O*/C | **C** | C |
| -1 | E | E | E | E | **C** | C | C |
| -5/-100/±2³¹ | O | O | O | O | **C** | C | C |
| 超int32 | E | E | E | E | E | E | E |

（O=OK/E=EXC/C=CRASH；\*dims=10 cbytes=32：Float32=OK，其余 dtype=CRASH——唯一分歧正是 itemsize 差异，反证模型自洽）

**统一规律**：
1. 崩溃阈值 = **写字节数 > glibc chunk usable size**（非 dims 期望大小）；0 字节缓冲最小 chunk 24B：写 ≤24B 静默、≥32B 覆盖相邻 header 崩
2. **"OK" ≠ 安全**：所有 content>SizeOf 的 OK case 实际都越界写了（静默堆污染）
3. **⭐ parameter.py 校验缺陷**：`if -1 in self.shape` 只查 -1，其他负值全绕过 → `dims=[-5]` 可**静默正常返回畸形 Parameter**（比 -1 更隐蔽的投毒向量）
4. 漏洞**类型无关**（Float32/Float16/Int4/Int8/UInt8/Bool 全中）

**方法论**：矩阵化审计（dims 边界 × 长度 × dtype）比逐个试高效，且能自动暴露校验逻辑的"只拦特定值"缺陷。

## 七.13、Task 1：RCE 尝试 + 多视角评审（"测试1"，08-07 晚）

**实证（2.8.0）**：
- 多 value 堆布局：[a溢出,b正常]→free() 检测 SIGABRT；[b正常,a溢出]→普通运行 SIGSEGV（控制流偏离）/gdb 下 SIGABRT@_int_free 或 **SIGSEGV@_int_malloc（遍历被 0x41 污染 fastbin fd）**——**攻击者字节进入 glibc 空闲链表 = fastbin 投毒原语成立**
- 溢出字节完全可控；崩溃模式 SIGSEGV/SIGABRT 不稳定（堆布局敏感）
- 畸形对象二次触发：dims=[-5] 静默返回 `shape=(-5,)` Parameter，asnumpy 抛 ValueError

**Workflow 多视角评审（3 视角 + 综合 + 对抗验证）最终结论**：
- **完整 RCE = UNLIKELY**（对抗验证修正）：glibc 2.35 safe-linking 循环依赖（构造受控 fd 需堆基址，唯一泄漏源"重叠→asnumpy"需先有受控重叠，自举不成）+ 无内置泄漏 + 一次性单进程无 ASLR 爆破窗口
- **CWE-787 内存破坏 = 真实、确定性、类型无关、崩溃可延迟** → 合格上报项，评级 **Medium-High**（不虚高 POSSIBLE RCE，也不降级为仅 DoS）
- **结构洞察**（最有价值）：tensor 数据缓冲是**叶子分配**（地址低于 TensorImpl/TensorDataImpl），前向溢出无法原位覆盖本 tensor 的 data_ptr/shape/refcount/vtable，只能破坏后分配 chunk 的 malloc 元数据 → 决定利用上限
- 威胁专家关键对比：PyTorch CVE-2026-24747（非可信 checkpoint 堆破坏 CVSS 8.8，仅 torch 2.10.0 修）、TensorFlow CVE-2021-41221（7.8）、MindSpore 自家 CVE-2025-3144（3.3，上报需预判的反例）

**方法论**：对抗验证（指定唱反调评审）能抓住"可行性评级过度乐观"的硬伤（循环依赖），是防止虚高上报的必备环节。

## 七.14、-5 畸形对象经 load_param_into_net 网络路径影响（方向 1，08-07 晚）

**场景矩阵**（Dense(2,2)，恶意 tag='unused'/'fc.weight'，cb=4B 纯畸形 / cb=28B 越界 4B）：
- 匹配 tag → RuntimeError "shape (2,2) vs (-5,)"（确定性异常，可 catch）
- **未匹配 tag 被静默跳过** → 推理/训练 3 步全正常（loss 正常下降）——**畸形 ckpt 能静默穿过生产训练流程**
- **cb=28B 变体：业务全正常（SKIP-INFER OK + 正常输出），进程退出时 rc=-6 `free(): invalid next size (fast)`**——**投毒在加载瞬间发生，与参数是否被使用无关**；崩溃延迟到任意点 = 隐蔽 DoS
- **save_checkpoint 对畸形参数 = 静默数据丢失（非二次投毒）**：serialization.py:517 `get_bytes()` 空 → `range(0,0,chunk)` 零次循环 → 空写。单参 dict=0 字节文件；混合 dict=畸形参数静默丢弃，正常保留。**修正中间假设：无传播路径**，是完整性缺陷

**结论**：畸形 ckpt 可穿过加载→推理→训练→保存全链路；cb≥25B 档"业务正常+延迟崩溃"是 CWE-787 在使用场景的实锤表现，补齐了"仅单次 load_checkpoint 崩溃"的短板。
