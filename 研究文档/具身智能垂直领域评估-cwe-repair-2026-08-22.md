# 具身智能垂直领域评估：cwe-repair 工具应用分析（2026-08-22）

> 背景：已完成 `cwe-repair` DSH skill（检测/修复/验证/可达性/覆盖度五组件），在 AimRT（AR-1）、
> AGIBOT（X1-9/X1-8/X1-10）、XR（VUL-02 pickle）真实漏洞上完成闭环演示，并在
> **NCNN 真实二进制上完成双向验证（修复版 PASS / 漏洞版 REVIEW）**。
> 本文评估该工具对"具身智能 AI 组件漏洞"这一垂直领域的适配性与进一步研究方向。

## 〇、真实验证结果（2026-08-22 WSL 实测，核心成果）

```
漏洞版（未修复 loadpoc_file_vuln）：
  恶意 149B → SIGSEGV (exit=-11)  crash  恶意 negidx → SIGABRT (exit=-6)  crash
  合法 valid_minimal → ret=0 正常
  判定: REVIEW ✅（工具正确识别"未修复"）

修复版（已修复 loadpoc_file_fixed2）：
  恶意 149B → ret=-1 拒绝   恶意 negidx → ret=-1 拒绝
  合法 valid_minimal → ret=0 正常
  判定: PASS ✅（工具正确验证"修复有效且无误伤"）
```

**方法论收获（真实环境暴露的 3 个语义差异，模拟测试无法发现）**：
1. `ret=-1` 输出在 **stderr**（仅捕 stdout 会漏判）；
2. 进程被信号终止时 returncode 是**负信号码**（-11/-6），crashed 判定须含负值；
3. "合法输入"须用**同版本格式兼容**样本（squeezenet 旧格式报 "param is too old" 非误拒）。

## 一、垂直领域适配性评估（基于本工具实测）

### 1.1 检测器在具身智能源码上的真实表现

| 组件 | 扫描文件数 | 命中数 | 命中已知漏洞 | 误报特征 |
|---|---|---|---|---|
| AimRT json_convert.h | 1 | 7 | ✅ L170（AR-1 越界写） | 6/7 为有守卫的正常代码 |
| AGIBOT control 模块 | 37 | 775 | ✅ controller_base.cc:21（X1-9）、control_module.cc:154（X1-10 除零） | 大量 `map[key]` 插入语义被误标（array_index_raw 过宽） |

**结论**：检测器**能命中真实漏洞**（X1-9 与 ASan PoC 位置一致，AR-1 与人工审计一致），
但**粗粒度**——775 个命中里绝大多数是正常代码（map 下标、有守卫的循环）。这是"规则模板
检测器"的固有形态：**粗筛后需 agent/人工确认**，而不是开箱即用的精确扫描器。

### 1.2 与通用工具的差距（诚实评估）

| 维度 | cwe-repair detect | CodeQL/cppcheck |
|---|---|---|
| 精确度 | 低（大量误报） | 中-高（数据流分析） |
| 模式贴合度 | 高（专为平行数组/外部索引设计） | 通用 |
| 可解释性 | 高（命中即给模式+证据） | 中 |
| 配置成本 | 零（python 直接跑） | 高（CodeQL 需 query 语言） |

→ detect 定位为"**轻量初筛器 + 方法论载体**"，不替代 CodeQL；真正的增量在 verify。

## 二、垂直领域特有的挑战（具身智能组件 vs 通用软件）

### 2.1 输入形态多样（工具已覆盖一部分）

具身智能组件的外部输入包括：**模型文件**（.param/.parambin/.ckpt/.onnx/.mnn）、
**配置文件**（YAML）、**消息**（ROS2/DDS/protobuf/JSON）、**场景资产**（MJCF/URDF）。
cwe-repair 的 detect 覆盖"源码层的索引/溢出/除零"，但**不覆盖输入格式本身的解析边界**
（如 MindSpore 的 dims vs content 不一致——那是跨字段逻辑校验，规则模板难表达）。

### 2.2 可达性分层（工具输出不含此信息）

具身智能漏洞的"默认可达 vs 配置后可达"差异巨大（XR 默认 0.0.0.0 绑定 vs AGIBOT
需配置 ros2 订阅）。当前 detect 输出不含可达性标注——**建议 v2 增加**（从 YAML 配置
读取 sub/publish 后端，标注默认可达性）。

### 2.3 修复验证的"物理后果"无法自动化

verify 验证的是"内存安全"（无崩溃、拒绝恶意输入），但具身智能漏洞的最终影响是
**物理动作**（关节指令、速度突破）——这无法在纯本地闭环中验证（需仿真器/真机）。
这是领域边界，也是上报材料中"物理影响待实机验证"的来源。

## 三、垂直领域增量价值（为什么值得继续做）

### 3.1 实证数据集稀缺性

[EAIR Software Bugs 实证研究](https://arxiv.org/abs/2507.18267)（arXiv 2507.18267）表明
具身机器人软件缺陷的**系统化实证研究较少**。本项目已有 5 组件 28+ 漏洞的完整数据
（源码位置/PoC/ASan/修复状态），是稀缺的垂直领域语料——可支撑"修复正确性验证"
在垂直领域的实证论文。

### 3.2 修复模式的统一性（工具的核心优势）

本项目实证：具身智能组件的越界漏洞**修复模式高度统一**（补一行 `if (idx<0||idx>=size)`），
NCNN PR #6922、AimRT AR-1、AGIBOT X1-9 的修复完全同构。这使"规则模板修复 + 双向验证"
在此垂直领域**比通用领域更有效**（模式越统一，模板越可靠）。

### 3.3 与 DSH agent 的协同（第四条工作流）

```
detect(粗筛) → agent 确认(上下文/可达性) → repair(模板补丁) → verify(双向回归) → report(PR 材料)
```
DSH 的 agent 能力补上了 detect 的误报短板（上下文判断），verify 补上了 LLM 修复的
无验证短板——**人机协同是此工具在 DSH 生态的差异化价值**。

## 四、下一步建议（按优先级）

1. **v2 增强 detect**：增加可达性标注（读 YAML 配置）+ 消除 map 下标误报
   （`operator[]` 的插入语义与越界读区分）；
2. **真实 NCNN 闭环**：恢复 WSL 后跑 `examples/ncnn_blobidx_verify.json`，
   用真实二进制验证 verify（这是论文最硬的证据）；
3. **数据集沉淀**：把 5 组件 28 漏洞整理为统一 JSON 数据集（file/line/CWE/修复/验证结果），
   作为垂直领域实证语料；
4. **论文定位**：「面向具身智能组件漏洞的修复正确性自动验证」——方法（双向回归闭环）
   + 垂直实证（28+ 漏洞）双增量。

## 五、诚实结论

- ✅ 工具可用：三阶段闭环在 AR-1 / X1-9 上演示成功，verify 逻辑经模拟测试验证；
- ⚠️ detect 是"初筛器"非"精确扫描器"：775 命中需 agent 确认，这是设计取舍不是缺陷；
- ⚠️ 垂直领域增量主要在 **verify 闭环 + 实证数据集**，不在 detect（红海）；
- ⚠️ 物理影响验证超出工具边界（需仿真器/真机，且受授权约束）。
