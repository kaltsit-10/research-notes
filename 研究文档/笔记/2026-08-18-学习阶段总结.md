导师提出可以继续积累具身智能 AI 漏洞，归纳不同漏洞之间的共同点，从而形成综述或论文；同时可以分享已经发现的漏洞，再共同判断能否开展真正的攻击验证。

据此，研究流程调整为：

```text
漏洞发现与源码审计
        ↓
最小复现与版本/修复状态核验
        ↓
统一案例登记与横向共通点归纳
        ↓
向导师分享漏洞与证据
        ↓
共同判断攻击价值、授权范围和实验边界
        ↓
```

关键改变是：**L3/L4 不再作为当前立即执行的任务**。在导师讨论前，先把“漏洞是否存在、为什么存在、影响到哪一层、是否已修复、是否公开”说清楚。

## 五、GenieSim 初步认识

### 5.1 它是什么

GenieSim（仓库通常写作 `genie_sim`）是 AgiBot 的具身智能仿真平台，可以理解为虚拟机器人实验室，用于：

- 模拟机器人和虚拟场景；
- 运行操作、移动等任务；
- 进行策略评测和 benchmark；
- 生成或收集仿真数据；
- 与 ROS 2、Isaac Sim 等组件结合。

它与 `agibot_x1_infer` 的区别是：

- `agibot_x1_infer` 更偏真实机器人推理与控制模块；
- `genie_sim` 更偏虚拟机器人、虚拟场景和任务评测平台。

### 5.2 硬件门槛的谨慎结论

目前不能把 GenieSim 简单描述成“完全不需要 GPU”。如果完整运行依赖 Isaac Sim、视觉渲染或高保真物理仿真，通常会受到 NVIDIA GPU、显存、驱动和 Isaac Sim 版本的限制；仅进行源码阅读、配置分析、Python 入口梳理或部分非渲染测试，硬件要求可能低得多。

因此，后续应把 GenieSim 拆成三种使用层级：

1. **静态研究层**：源码、配置、资源加载器和数据处理路径，不需要运行完整仿真；
2. **轻量验证层**：只运行可在 CPU 或低配置环境启动的模块，需以官方依赖声明和本地实测为准；
3. **完整仿真层**：Isaac Sim、渲染、物理和大规模 benchmark，可能需要较强 GPU，不能预先承诺普通电脑可运行。

本日只完成概念和路线层面的判断，没有把 GenieSim 安装成功或完整运行写入成果。

## 六、统一漏洞案例记录格式

为了后续归纳共通点，每个漏洞统一记录以下字段：

| 字段 | 记录内容 |
|---|---|
| 组件与版本 | 精确 tag、commit、构建选项 |
| 输入类型 | 模型、配置、消息、场景资产或其他外部数据 |
| 信任边界 | 输入从何处进入、默认是否可信、是否需要本地权限 |
| 解析入口 | 函数、文件和源码行号 |
| 根因模式 | 长度未校验、索引未校验、整数溢出、异常处理等 |
| 触发条件 | 最小输入、必要环境和确定性 |
| 影响类型 | 资源耗尽、崩溃、越界读/写、异常接受或数据完整性问题 |
| 证据等级 | 实测、源码确认、第三方公开记录、待验证 |
| 修复状态 | 未修、修复提交、上游合入、已发布版本 |
| 公开状态 | 未公开、私密披露、公开公告或已知重复 |
| 具身关联 | 感知、规划、控制、仿真、部署供应链等 |
| 导师讨论状态 | 尚未讨论、已分享、待决定攻击验证 |
| 可公开材料 | 哪些日志、PoC 和字节布局可以对外使用 |

### 预期归纳的共通模式

- 模型/配置/消息被当作可信输入，缺少长度和范围校验；
- 二进制与文本、真实与仿真、不同加载入口之间的修复不对称；
- 计数、维度和数组长度不一致导致资源耗尽或越界；
- 错误返回路径与正常路径的资源清理不一致；
- 外部模型供应链把“数据文件”转化为高复杂度解析和执行入口；
- 局部模块的安全检查无法自动保证跨模块接口安全。

这些是待由更多案例验证的研究假设，不能在证据不足时写成普遍定律。
