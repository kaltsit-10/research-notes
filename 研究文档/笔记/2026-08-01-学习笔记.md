# 2026-08-01 学习笔记

## 核心收获
今天就是从fuzz一个自己写的代码到了fuzz一个ONNXruntime库
### 1. ONNX Runtime 是什么
AI模型的"可执行文件格式"和"运行时引擎"。所有用 PyTorch 训练的模型，部署到机器人/手机上时都要先导出为 `.onnx` 格式，再由 ONNX Runtime 加载执行。**它卡在所有 AI 模型和所有硬件之间——攻击了它，就攻击了整条 AI 供应链。**

### 2. 今天对什么做了 fuzz
`onnx::ModelProto::ParseFromString()`——ONNX 模型文件的底层解析器。任何 `.onnx` 文件被加载时，字节流先经过 Protobuf 的 `CodedInputStream`，再经过 ONNX 的 `ModelProto` 反序列化。我们直接 fuzz 最外层入口。

### 3. 怎么编译的
系统包版本冲突 → 自己从 GitHub 下载 `onnx.proto` 源码 → `protoc --cpp_out` 生成 `.pb.h/.pb.cc` → `clang++ -fsanitize=fuzzer,address` 编译 harness → 链接 `libprotobuf`。

### 4. Fuzz 结果
- 50万次/91秒，0 crash
- 有 ONNX 模型种子（用 Python `onnx` 库生成的合法 105 字节模型）
- 零 crash 是正常的——真实漏洞需要跑得更久、喂更多种子

### 5. 关键理解
```
你以前想的：         实际的攻击路径：
ONNX Runtime →       ParseFromString → 图校验（check_model）
完整编译它再fuzz      只需要fuzz一个函数入口即可
                      绕过了编译整个引擎的麻烦
```

### 6. Fuzz 不只是"变态输入"
Fuzz 是一个**自动化探索程序状态的引擎**，输入变异只是手段，真正驱动它的是**代码覆盖率**。

```
你以为的 fuzz：                    实际的 fuzz：
给变态输入 → 看崩不崩              给输入 → 触发了新代码路径？
                                            ↓
                                  保留这个输入，以此为起点继续变异
                                            ↓
                                  覆盖率是"指南针"，
                                  自动探索越来越深的代码
```

fuzz 界面里的 `cov: 6` = 触发了 6 个代码块——**这个数字才是 fuzzer 真正在乎的**，crash 只是副产品。

### 7. Fuzz 的几类玩法

| 类型 | 做什么 | 我用过吗 |
|------|--------|---------|
| **变异型** | 拿种子，随机改字节 | ✅ `./fuzz_onnx corpus/` |
| **生成型** | 按协议/格式语法生成合法结构 | ❌ |
| **覆盖率引导** | 用代码覆盖率决定保留哪些输入 | ✅ libfuzzer 自动做的 |
| **符号执行** | 数学求解"能走到某行的精确输入" | ❌ |
| **差分fuzz** | 同样输入喂给两个相似程序，看输出是否一致 | ❌ |

### 8. "输入"不只是文件

| 输入形式 | 例子 |
|----------|------|
| **文件输入** | `.onnx` 模型文件（今天做的） |
| **网络输入** | ROS 2 topic 消息、DDS RTPS 包 |
| **API 序列** | 函数调用的顺序——先 `create()` 再 `destroy()` 再 `create()` 可能触发 use-after-free |
| **环境变量** | 某些程序读 `HOME`/`PATH` 时有 bug |

### 9. 除了 fuzz，挖漏洞还有哪些方法

| 方法 | 做什么 | 和 fuzz 的关系 |
|------|--------|---------------|
| **静态分析** | 不运行，扫源码找 bug 模式 | fuzz 是"跑着找"，静态分析是"看着找" |
| **符号执行** | 数学求解"走到第N行的精确输入" | fuzz 快但浅，符号执行深但慢，互补 |
| **人工代码审计** | 人肉读代码找逻辑漏洞 | fuzz 找内存 bug 强，人找逻辑 bug 强 |
| **补丁对比** | 比对新旧版本 diff，定位刚修掉的漏洞 | 去挖类似的 |

我最好的策略：**fuzz（自动化广度）+ 人工审计 fuzz 覆盖不到的逻辑（人工深度）**。

### 10. 今天 fuzz 的实际工作流程

```
corpus/seed.onnx (105字节合法模型)
         ↓
  libfuzzer 自动变异
         ↓
  每变异一次 → 喂给 ParseFromString
         ↓
  "覆盖了新代码吗？"
    ↓           ↓
  是 → 加入语料  否 → 丢弃
         ↓
  "崩了吗？" → ASAN 监控
    ↓           ↓
  崩了→保存crash  没崩→继续
```

91秒50万次零crash，`cov: 6`——需要更多结构多样的种子让 fuzzer 探索更深。

## 今天跑通的命令链

```bash
# 1. 下载 proto 源码
curl -sL https://raw.githubusercontent.com/onnx/onnx/main/onnx/onnx.proto

# 2. 编译 proto → pb.h/pb.cc
protoc --cpp_out=onnx_gen onnx_gen/onnx.proto

# 3. 编译 fuzz harness
clang++ -fsanitize=fuzzer,address -I onnx_gen -o fuzz_onnx \
  fuzz_onnx.cc onnx_gen/onnx.pb.cc -lprotobuf

# 4. 生成 ONNX 种子
python3 -c "import onnx; ..."  →  corpus/seed.onnx (105字节)

# 5. 跑 fuzz
./fuzz_onnx corpus/ -max_len=65536 -runs=500000
```

## crash 分析工具预习：c++filt 和 gdb

### c++filt——破译编译器乱码

C++ 编译器会把函数名"搅碎"（name mangling），crash 栈帧里全是乱码：

```bash
$ c++filt <<< "_ZNK4onnx10ModelProto14ParseFromArrayEPKvi"
onnx::ModelProto::ParseFromArray(void const*, int)
```

以后 ASAN 报错里的函数名用这个翻译。

### gdb——事发现场回放

```bash
# 当 fuzz 出了 crash，用 gdb 加载崩溃文件：
gdb ./fuzz_onnx crash-xxxxx

# 关键命令：
(gdb) bt           # backtrace → 崩溃时的完整调用栈
(gdb) info locals  # 看每个局部变量的值
(gdb) print ptr    # 看某个指针指向了什么
```

等 fuzz 出第一个 crash 后实际操练。
